# 乘用车用户洞察智能体：代码审计与第一阶段最小可行开发方案

审计日期：2026-10-30  
审计项目：`E:\AI\data\envs\helloagent\myproject`  
审计范围：AgentScope 初始化、Tool/MCP、Workflow、RAG/WeKnora、PostgreSQL/pgvector、前端消息协议、任务状态、证据引用、真实访谈数据可用性  
本次结论：**不重构现有智能体系统，不做页面布局改造。允许实施一条独立的“用户访谈证据问答”纵向切片。**

## 一、审计结论

1. 当前项目实际使用 **AgentScope 2.0.3**，不是 2.0.4 dev；`requirements.txt`、安装包元数据和运行时导入均已核对。
2. 用户洞察 Agent 的初始化方式是 `Agent + ReActConfig + Toolkit`，每次 Web 请求新建 Agent，不保留会话状态。
3. 现有用户洞察工具 `user_insight_tagger` 是规则/词典打标器，不是访谈库检索器；它不能返回某位受访者的真实原文、题号和秒级时间。
4. 当前项目没有接入 WeKnora，也没有可用的访谈 pgvector 检索工具。`mcp/vector_store/` 只有占位说明。
5. 旧 `rag-engine` 确有 PostgreSQL/pgvector、Embedding 和 Reranker 能力，但它是另一套独立工程，表结构只适合文档 chunk，不具备“受访者—题号—证据—秒级时间—标签”的证据链。
6. 当前 Web 服务实际是 Python 标准库 `ThreadingHTTPServer`，不是 FastAPI。第一阶段不应为了追求框架统一而重写服务层。
7. 当前页面没有 SSE：`/api/chat` 和 `/api/assistant/chat` 都是阻塞式 POST + 完整 JSON；页面进度条是前端定时动画，不是后端真实事件。
8. 当前没有类型化证据引用机制。页面只能展示 `answer` 和 `tool_events`，不能点击回到原始访谈与时间戳。
9. 第一阶段可行路径是：**新增独立访谈 schema + 检索服务 + 一个 AgentScope Tool + 一个独立 API 分支 + 结果区内证据卡片**。不触碰市场战略 Agent、预测功能、现有页面布局和现有 `/api/chat` 语义。
10. 第一阶段优先使用现有 pgvector/Embedding/Reranker，不建议把 WeKnora 作为访谈精确证据的主存储。WeKnora 可以保留为后续文档型知识检索通道。

## 二、AgentScope 2.0.3 现状

### 2.1 版本与环境

| 项目 | 审计结果 |
|---|---|
| Python 解释器 | `E:\AI\data\envs\helloagent\Scripts\python.exe` |
| AgentScope | `2.0.3` |
| 安装位置 | `E:\AI\data\envs\helloagent\Lib\site-packages\agentscope` |
| 依赖声明 | `requirements.txt` 固定 `agentscope==2.0.3` |
| Web 框架 | `http.server.ThreadingHTTPServer`，不是 FastAPI |
| 常驻异步循环 | `AgentEventLoopRunner`，用线程持有单一 asyncio loop |
| 并发控制 | `AGENT_RUN_LOCK` 串行化 `/api/chat` 请求 |

### 2.2 Agent 初始化

`agents/user_insight_agent.py` 的实际写法：

```python
from agentscope.agent import Agent, ReActConfig
from agentscope.tool import Toolkit

Agent(
    name=agent_cfg["name"],
    system_prompt=USER_INSIGHT_CONFIG_PROMPT,
    model=build_model(config),
    toolkit=Toolkit(tools=tools),
    react_config=ReActConfig(max_iters=int(agent_cfg.get("max_iters", 6))),
)
```

结论：

- 使用 AgentScope 的 `Agent` 与 ReAct 循环。
- 每次 `run_agent_once()` 都重新构建 Agent；没有 `AgentState` 持久化，也没有 `session_id` 级会话记忆。
- 当前系统提示词要求输出固定七章配置建议，不适合作为“只根据访谈证据回答并引用原文”的严格证据型 Prompt。

### 2.3 Tool/Toolkit 注册

- 业务工具继承 `ReadOnlyBusinessTool -> ToolBase`。
- 每个工具声明 `name`、`description`、`input_schema`，实现 `check_permissions()` 与 `call()`。
- 返回值使用 `ToolChunk(content=[TextBlock(...)])`。
- `build_business_toolkit()` 返回工具列表，再由 `Toolkit(tools=tools)` 注册。
- 当前工具包括搜索、网页读取、天气、Tavily、Playwright、Agent Reach 和规则型 `user_insight_tagger`。

可复用点：

- 新增 `interview_evidence_search` Tool 不需要引入新 Agent 框架。
- 检索工具应继承同一 `ReadOnlyBusinessTool`，并在 `call()` 内只执行白名单查询。

必须补强：

- 当前 `UserInsightTaggerTool` 只做关键词命中，不读取现有访谈数据。
- 该工具的 `evidence_quotes` 是从传入文本切句，不是持久化证据，也不是可追溯引用。
- 不能把该工具的输出直接当作“真实受访者原话证据”。

### 2.4 MCP 接入

当前实现位于 `integrations/market_mcp_plugins.py`：

- 使用 `agentscope.mcp.HttpMCPConfig` 与 `MCPClient`。
- 四个插件：政策、权益、新车、口碑。
- 通过 `MCPClient(...).list_tools()` 发现工具，再将其追加到 Agent 的 Toolkit。
- 每次请求按 `agent_key` 和用户选择动态发现插件；单个插件失败不会移除其他插件。

结论：

- MCP 接入方式可复用，但现有四个插件都不是用户访谈检索服务。
- 第一阶段直接新增 Python Tool 更快、更可控；不要为了访谈检索先造一个新的 MCP Server。
- 后续如果访谈检索要跨系统复用，再将该 Tool 背后服务包装成 MCP，不改变 Agent 调用契约。

### 2.5 Workflow 实现

当前没有使用 AgentScope 的 pipeline/Workflow 编排器。实际存在两套“流程”能力：

1. `SkillRunContext`：持久化 `run-state.json`、任务图、checkpoint、artifact 与独立验收，服务于 Skill 类任务。
2. 前后端后台任务：周报、预测、月报、宏观月报使用 Job Manager + 轮询接口。

用户洞察目前没有独立工作流；`/api/chat` 只是一次 ReAct 调用、可选重试和可选质量修订。

第一阶段不建议引入新 Workflow 引擎。推荐用一个确定性的服务层完成“过滤 → 召回 → 重排 → 证据打包”，再交给 AgentScope Agent 组织最终回答。这样不会让“是否检索到真实数据”取决于模型的工具选择随机性。

现场探活：

- 根页面/健康检查返回 HTTP 200。
- 现有知识库能力来自独立 WeKnora 工程，不属于当前 AgentScope 项目。

WeKnora raw retrieval 的典型字段为：

```json

  "id": "chunk_...",
  "content": "...",
  "knowledge_id": "doc_...",
  "knowledge_title": "...",
  "chunk_index": 4,
  "score": 0.82,
  "match_type": "hybrid",
```

- WeKnora 适合文档级问答与 chunk 召回，不适合作为第一阶段访谈证据主存储。

### 4.2 SSE

结论：**当前没有 SSE**。

- 代码中没有 `text/event-stream`、`EventSource` 或 `StreamingResponse`。
- 前端用 `fetch()` 等待完整 JSON。
- 工作台中的五阶段进度由 `startDemoProgress()` / `startExecutionNarrative()` 前端定时器模拟，不是后端真实阶段事件。
- `/api/chat` 最长等待 180 秒，宏观/技能任务另有 300 秒边界。

AgentScope 2.0.3 本身已提供：

```python
agent.reply_stream(UserMsg(...))
```

可产生文本增量、工具调用、工具结果等事件。因此未来加入 SSE 不需要更换 AgentScope，也不需要引入重型框架。

### 4.3 任务状态

- `/api/chat` 没有先返回 `run_id` 再轮询的通用任务机制。
- 周报、预测、月报、宏观月报另有后台 Job Manager 与 `/jobs` 查询接口。
- `project_runs.json` 在请求完成后保存报告与工具事件，不是实时任务状态。

### 4.4 证据引用

- `tool_events` 只能说明“调用了什么工具”，不能说明“回答中的哪句话来自哪条访谈原文”。
- `mcp_plugins` 只报告插件状态。
- 页面没有证据卡片、时间戳、原文定位或点击回源。
- 模型正文中的来源表述没有后端结构校验。

### 4.5 会话

- `/api/chat` 不带 `session_id`。
- 每次请求重新构建 Agent。
- 无跨轮对话记忆；追问依赖前端把历史拼回问题，当前工作台并未稳定实现这一点。

```json
  "question_id": 4,
  "question_text": "用户此次购车的主要原因是什么？",
  "quote": "我原来开的是宝马X3……",

  "time_precision": "second",
  "confidence": "非常自信",
  "source": {
    "source_format": "answer_json",
    "source_version": "20261008",
    "document_id": "R045-Q004",
    "checksum": "sha256:..."
  },

    "score": 0.913,
```

- `evidence_id` 必须是运行内稳定编号，可回查到 source_checksum。

## 七、访谈检索服务设计

### 7.1 检索流程

```text
问题
  → 白名单解析 filters
  → PostgreSQL 结构化过滤
  → answer embedding 向量召回 top 30
  → 标签/题号辅助召回
  → 现有 Reranker top 8
  → 按受访者/题号去重
  → 取 evidence 明细
  → 生成 E1..En
  → AgentScope Agent 只基于证据组织回答
  → 后端校验 [E#]
  → 返回 answer + evidence + retrieval meta
```

### 7.2 过滤字段

第一阶段只开放：

- `city`
- `vehicle_model`
- `purchase_type`
- `question_ids`
- `tag_names`
- `tag_values`
- `respondent_codes`

不开放任意 SQL、任意列名、正则表达式或文件路径。

### 7.3 检索策略

1. 先做结构化过滤，避免跨城市/车型污染。
2. 每问答案作为主要检索单元，不是整份长文档 chunk。
3. 问题文本 + 答案文本 + 标签名/值拼接后做 embedding。
4. 初始召回 30 条，重排后最多 8 条证据。
5. 同一受访者最多 2–3 条证据，避免单人占满结果。
6. 无匹配时明确返回空证据，不允许模型用通用知识补写访谈观点。
7. Reranker 失败时降级为向量分数，并在 metadata 标记 `reranker_degraded=true`。

### 7.4 性能边界

- 单次检索超时：3 秒。
- Reranker 超时：8 秒。
- 模型回答超时：30 秒（第一阶段证据问答不需要 180 秒长报告）。
- 结果默认 6 条，最多 8 条，避免上下文过长。

## 八、第一条纵向闭环

目标：

```text
网页提问
  → 独立用户洞察 API
  → AgentScope 2.0.3
  → 访谈证据检索服务
  → 原文 / 题号 / 说话人 / 时间戳
  → 页面显示回答与证据卡片
```

### 实施步骤

1. 建立 `user_insight` schema、导入 63 人数据。
2. 为 `answer` 与 `tag` 生成 1024 维 embedding。
3. 实现 `InterviewRetrievalService`：
   - 白名单过滤；
   - 向量召回；
   - Reranker；
   - 证据格式化。
4. 实现 `interview_evidence_search` AgentScope Tool。
5. 在 `run_agent_once` 新增 `agent_key == "user_insight_config"` 且 `analysis_type == "interview_evidence_qa"` 的隔离分支：
   - 先执行确定性检索；
   - 把证据包注入 Agent 提示；
   - Agent 只负责归纳与引用；
   - 后端用检索结果生成最终 `evidence[]`。
6. 新增 `POST /api/insight/interview/query`，不改 `/api/chat`。
7. 在现有结果区域末尾追加证据卡片，不改变页面结构。
8. 增加引用校验、无证据处理、检索故障降级。

### 推荐响应行为

- 有证据：回答 2–5 条归纳，正文使用 `[E1]`、`[E2]`。
- 无证据：明确写“当前访谈库中没有足以支持该结论的原话”，`evidence=[]`。
- Reranker 失败：仍返回向量结果，页面显示“重排服务降级”。
- 数据库不可用：返回明确错误，不用模型常识冒充访谈结论。

## 十二、测试方法

### 12.1 数据测试

- 63 个标签工作簿都有 `85` 个标签行。
- 63 个 DOCX 都有 Q1–Q85。
- 61 个 JSON 能按 UTF-8 BOM 兼容方式读取。
- `胡毅-唐L` 的 `Q1...Q85` 被规范化为整数 1–85。
- 无证据时间时 `time_precision` 不等于 `second`。
- 证据 `start_sec <= end_sec`。
- 65,000+ 证据字段无空 `quote_text`。

### 12.2 检索测试

示例问题：

```text
沈阳小米YU7换购用户为什么选择这款车？
哪些用户提到后排空间和孩子？
增购用户的预算关注点是什么？
```

验证：

- 城市过滤后不返回其他城市。
- 车型过滤后不返回其他车型。
- 返回的 `question_id` 与 filter 一致。
- 每条证据能回查到 `interview_id + question_id + start_sec + end_sec`。
- 无匹配时返回 `evidence=[]`，不返回泛化观点。

### 12.3 API 测试

```powershell
Invoke-RestMethod `
  -Uri 'http://127.0.0.1:7860/api/insight/interview/query' `
  -Method Post `
  -ContentType 'application/json' `
  -Body '{"question":"哪些用户提到后排空间？","filters":{"city":["沈阳"]},"top_k":6}'
```

断言：

- `status == "completed"`
- `evidence` 是数组
- 每条证据有 `evidence_id`、`quote`、`time_label`、`source`
- 正文中的 `[E#]` 全部能在 `evidence` 中找到
- 无证据时不出现虚构引用

### 12.4 回归测试

- 市场战略 Agent 的原有 `/api/chat` 请求保持兼容。
- 首页 `/api/assistant/chat` 不受影响。
- 预测、周报、月报接口 URL、参数、返回字段不变。
- 页面布局、导航、卡片结构不变。

## 十三、风险与控制

| 风险 | 影响 | 控制 |
|---|---|---|
| 访谈含姓名、城市、车型等 PII | 越权或外发风险 | API 默认只返回匿名编号；日志不写原话；内部权限分级 |
| 2 人无秒级证据 | 证据链不完整 | 明确 `time_precision=paragraph`，不伪造时间 |
| JSON BOM/题号类型不一致 | 导入失败或题号错位 | 导入器统一 `utf-8-sig` 与 `Qn` 解析 |
| 模型编造引用 | 业务误判 | 后端生成 evidence，校验 `[E#]`，无证据拒答 |
| WeKnora/旧 RAG 无结构化题号与时间 | 无法精确追溯 | 第一阶段用专用 schema，不混用现有 chunk 表 |
| 现有服务非 FastAPI | 不能假装已统一技术栈 | 第一阶段沿用 ThreadingHTTPServer；FastAPI 迁移另立任务 |
| `AGENT_RUN_LOCK` 串行化 | 并发低 | 第一阶段单用户演示足够；后续按 run queue 改造 |
| 定性样本与定量样本口径不同 | 误把原话当比例 | Prompt 与页面同时标注“定性证据，不可计算人群比例” |
| `rag-engine` 硬编码凭据 | 安全与维护风险 | 新服务只读环境变量/密钥管理；不复制凭据 |
| reranker 服务波动 | 检索排序下降 | 超时降级向量排序，保留 `retrieval_meta` |
| 文本中的指令注入 | 模型越权 | 访谈原文按不可信数据处理；系统提示禁止执行原文指令 |

## 十四、第一阶段验收标准

必须全部满足：

1. 63 位受访者的 85 题与标签均可追溯。
2. 61 位有秒级证据；2 位明确为段落证据。

4. 页面能在现有结果区显示至少 1 条证据，包括题号、时间、说话人、原文和匿名受访者编号。
5. 无证据时明确拒答，不编造。
6. 市场战略 Agent、预测功能和首页布局回归通过。
7. 不新增重型 Agent 框架，不修改现有 `public` RAG 表。
