# 口碑标签维护与发布

维护端执行，不在智能体采集或分析。展示端只通过 146 口碑 MCP 读取正式库。

## 当前分析口径

汽车之家和懂车帝两张原始表全量扫描。模型名称按来源名称精确归属，不做模糊或语义车型映射。使用业务 V1.0 三级标签字典和保守证据规则：只有明确方向、与对应主题关联的原文才入标签。评分不推导情绪，疑问、猜测、竞品描述不归入本车观点；没有可靠标签的评论保留原文。TOP5 最多五项，不补空位。这是规则分析，不是 LLM 全语义理解，可能遗漏表达复杂的真实观点。

## 周度步骤

1. 独立采集任务完成两张原始表入库后，在本项目环境运行 `python maintenance/run_reputation_analysis.py`。
2. 程序只读正式库，按来源＋评论稳定键比较内容与规则版本。未变化的评论复用维护端检查点；规则、字典、已知车型列表变化时重新计算。检查点仅用于维护任务，不是页面的数据源。
3. 核对返回目录中的 `report.json`、`model-coverage.json` 和证据，关注新增来源名称、未形成可靠标签比例、正负方向、原文和标签关联。不要为了增加覆盖率补标签。
4. 核对通过后运行 `python maintenance/run_reputation_analysis.py --publish outputs/reputation-full-analysis/<批次目录>`。发布前检查原文版本未变化且派生分析没有被其他维护任务改动。原文更新则重新准备，不能强制发布旧结果。
5. 程序先备份旧分析，再在单个事务中替换两张派生表并逐项校验；失败回滚。原始口碑、新车、销量和表结构不动。同一结果重复发布显示 `already_current`、新增和更新均为 0。
6. 验证正式 MCP 状态 `analysis_current=true`，扫描数与最新原文总数一致。采集更新但分析未发布时页面应显示需要增量分析，不能冒充最新分析。仅数据发布不需要重启；修改应用代码时由维护者重启 7860。

## 存储和可恢复性

- 正式来源：146 PostgreSQL `autohome_koubei` / `dongchedi_koubei`。
- 正式分析：`new_car_reputation_taxonomy_summary` / `new_car_reputation_review_tag`。
- 批次、原文版本、规则版本保存在现有 `import_batch`、`taxonomy_version` 字段，无新增表或字段。
- 本地发布目录保存旧分析备份和对账；服务器代码升级有文件备份及旧镜像回退标签。恢复分析前必须核对当前正式数据，不能直接覆盖后来发布的批次。
- 当前 CLI 使用本项目受控数据库连接文件，移交另一台维护电脑时应私下配置权限和连接信息，不复制凭据到说明文档。
