## 0. 结论先行

**建议做，但按「函数调用单智能体 + 单车型只读取数工具」的 MVP 做；不做多智能体规划，不做上下文拼接，不做跨车型对比。**

| 决策项 | 结论 | 关键理由 |
| --- | --- | --- |
| 做不做 | 做 | 现有自由问答 Agent 已具备工具编排、证据编号、反幻觉门、流式链路，复用度约 60–70%，新增集中在「单车型取数工具 + 前端块 + 数字校验」 |
| 技术路线 | 函数调用单智能体（路线 B） | 数字必须由代码算；单智能体即可覆盖「三路取数 → 综合结论」，多智能体规划在此问题域没有确定性收益 |
| 用不用 AgentScope | 用，但只当执行框架 | 项目已用 2.0.3 的 `Agent + ReActConfig + Toolkit` 构建单智能体；不需要再引入多智能体编排层 |
| 范围 | **单车型**：靶心＝页面当前选中车型；不做 A vs B 对比 | 用户 2026-11-11 锁定范围 |
| 首版规模 | P0 4 个工具、5 条可验收指令；P1 扩到 8 个（含流通占位） | 先证明「数字可信 + 出处可查」，再扩数据源 |
| 最大阻塞 | 流通数据业务尚未接入（库内仅有口径未标注的销量表，按「未接入」处理）；深访单车 3–4 人，只能出原话不能出比例 | 见 §2.3、§2.5，直接决定首版能回答什么问题 |

一句话判断：**这是一个「复用已有 Agent 骨架 + 补单车型取数工具 + 补一层数字校验」的工程，不是一次新的架构建设。** 首版 3 人日可到可用，完整版 6–8 人日。

**必须写进方案的四条限制**：

1. **当前无上险 / 终端 / 保险 / 注册数据源，且正式流通数据尚未接入。** 需求把这一路称为「流通数据」，库内只有口径未标注的销量表。**本期按「未接入」处理**：工具接口先定义，调用返回空态「流通数据未接入」，模型不得用销量表顶替、不得估算。
2. `sales_import.source_caliber` 全表为空，无法判断是批发、零售还是合格证口径，即便后续接入也必须先由业务确认口径。

4. 任一正式流通源接入后，口径表述只允许「销量」，**不得写成「上险量」「终端交付」「市占率」**，除非新源本身提供了明确的上险/终端口径。

### 2.4 靶心口径：由页面当前选中车型决定

- 目标车型固定为下拉中的五款在库车型：零跑B10、铂智3X、iCAR 超级V23、海狮05、钛3（见 `config/analysis_models.json`）。
- **靶心 = 页面当前选中的那一款**，不写死任何一台；结论、取数、缓存键都以该车型为唯一主体。
- **不做跨车型对比**（用户 2026-11-11 锁定）：不提供 A vs B 参数、不提供对比入口、不生成对比结论；用户若要对比，引导用上方标准化磁贴逐车查看。
- 原型截图里的「埃安 RT」只是原型自带的界面示例车，**不是目标车型**，不参与任何口径、不作备选、不写入配置。
- 三路数据按单车型均可取：定量 30–41 人/车、深访 3–4 人/车、流通待接入（见 §2.1、§2.2、§2.3）。

## 3. 三条路线对比与取舍

### 3.1 对比

| 维度 | A 纯大模型 + 上下文拼接 | B 函数调用单智能体 | C AgentScope 多智能体规划 |
| --- | --- | --- | --- |
| 数字来源 | 预先拼进 prompt 的数字；未覆盖的指标模型会「补」 | 每次由工具 SQL 现算 | 同 B，但经多角色转述 |
| 数字可信度 | 低（长上下文里模型会改写、四舍五入、张冠李戴） | 高（数值只在工具返回值里出现） | 高（但多一跳转述，仍需校验） |
| 覆盖自由度 | 只覆盖拼接进去的固定视图，指令一变就缺数据 | 中高，按需取数 | 最高 |
| 延迟 | 5–10 秒（单次生成） | 15–40 秒（2–6 次工具 + 生成） | 40–120 秒 |
| 单次成本 | 1 次调用（但上下文最长） | 2–6 次调用 | 6–15 次调用 |
| 可审计性 | 只有一段文字，无法回溯 | 每次工具调用都有名称、参数、结果，可直接渲染成调用清单 | 有，但需要额外的角色级日志治理 |
| 与现有代码的复用 | 需另建数据拼装层 | 复用 12 工具骨架、证据注册、`[E#]` 反幻觉门、NDJSON 流式 | 需新建编排层，现有链路不覆盖 |
| 主要风险 | 幻觉数字、口径混淆，且难以事后发现 | 选错工具、题号猜错、迭代超时 | 规划不稳定、成本高、调试成本高 |
| 适配本项目程度 | 低 | **高** | 中 |

### 3.2 逐条取舍理由

**排除 A（纯大模型 + 上下文拼接）。** 这个模块的价值前提是「跨模块综合」，而跨模块意味着一次要并入画像 9 个分段、关注 16 维、战胜战败 2 套 16 维、满意度 16 维 + 口碑正负 TOP5 + 销量序列，拼完轻松过万 token。上下文越长，模型对具体数字的保真度越差；更关键的是，命令一旦超出预拼范围（例如「钛3 和海狮05 在智驾上的差距」），A 路线只能生成看起来合理的数字。项目已有明确的硬规则「模型散文永远不是证据」、「不得使用前端硬编码步骤冒充真实 Agent 执行」，A 路线与这两条直接冲突。

**排除 C（AgentScope 多智能体规划）。** AgentScope 2.0.3 本身已在项目中使用（`Agent + ReActConfig + Toolkit`，[user_insight_agent.py](file:///E:/AI/data/envs/helloagent/myproject/agents/user_insight_agent.py#L10-L17)），所以「用 AgentScope」不是新增成本。但多智能体的收益来自**子任务可并行、角色边界清晰、上下文互相隔离**——在本问题域里，五个数据源是串行依赖的（先定车型 → 再取指标 → 再综合），角色拆成「画像 Agent / 关注 Agent / 战胜战败 Agent / 报告 Agent」后，每个角色仍然只是调 1–2 个工具，收益接近于零，代价是：轮次翻倍、延迟翻倍、失败点翻倍、每次跨角色转述都可能损失一次数字精度。**这一层不值得。**

**选择 B（函数调用单智能体）。** 三条理由：

1. 项目已有一份跑通的实现。`build_user_insight_free_qa_agent` 已是「ReAct 单智能体 + Toolkit + 提示词里的工具选择决策表」，并且配套了证据注册、`[E#]` 校验、工具调用清单、NDJSON 流式。把这些搬到竞品洞察，是复制 + 裁剪，不是新建。
2. 数字可控。工具只返回「已算好的 count / n / ratio / 样本标记」，模型的任务被压到「选择取什么、怎么解释」，不承担算术。
3. 可审计。`record_tool_call` + `tool_events` 现成，前端可以把「这次结论用了哪几次取数」直接摊开给业务看，这是本项目最需要的信任机制。

### 3.3 推荐架构（一句话版）

```
前端「智能化分析」块
   └─ POST /api/bci/analysis/agent/stream  (NDJSON)
        └─ BCIAnalysisAgent (AgentScope Agent + ReActConfig, max_iters=8)
             ├─ 只读工具（P0 4 个 T1/T2/T3/T6；P1 扩到 8 个，含流通占位 T7）
             ├─ 数字白名单校验器（结论中的每个数字必须能在工具结果中找到）
             └─ 出处渲染（指标 / 数值 / 分母 / 题号或表名 / 时间窗）
```

**独立 Agent，不复用 `/api/insight/agent/stream`。** 项目硬约束是「不得修改智能问答链路」，而两者上下文不同（一个面向全库自由问答，一个绑定页面当前选中的单一目标车型）、提示词不同、工具子集不同。建议新增 `build_bci_analysis_agent`，与现有 Agent 并存，互不引用。

## 4. 工具清单

设计原则三条：

1. **粒度停在「已聚合的指标」**：工具返回分布 / TOP / 比值 / 样本标记，不返回原始明细行。原始明细直出会诱导模型自己算，也会把上下文撑爆。
2. **每个返回都自带口径**：`n`、`answered`、`sample_flag`、`question`（题号）或 `table`（表名）、`as_of`。
3. **能复用就复用**：优先包 `AnalysisService` / `PostgresReader` 的既有方法，不为工具重写 SQL。

### 4.1 核心工具（6 个；P0 先落 T1 / T2 / T3 / T6，T4 / T5 在 P1 补齐）

> 全部单车型签名：`model` 只有一个，**无 `models[]`、无 `compare_with`、无「竞品是谁」入参**。

## 5. 口径与安全约束

### 5.1 小样本：沿用现有阈值，不新增门槛

> 下表全部是项目已实施的常量与规则，本方案**不新增任何样本门槛**（引用自 `analysis_service.py` 与 `tasks/BCI-006/TASK.md` §5）。

| 场景 | 规则 | 现有实现 |
| --- | --- | --- |
| 车型定量样本 < 10 | 不出比例，只给人数 + 原因 | `ratio_payload`（[L177-L195](file:///E:/AI/data/envs/helloagent/myproject/competitor_insight/server/analysis_service.py#L177-L195)） |
| 单题作答 < 10 | 同上，按题判 | 同上 `answered` 分支 |
| 战败行 | 该行 < 5 人或对比总数 < 10 → 只给人数 | `_loss_split.ratio_of`（[L1049-L1061](file:///E:/AI/data/envs/helloagent/myproject/competitor_insight/server/analysis_service.py#L1049-L1061)） |
| 深访 | 3–4 人，永久不给比例；必须标「来源：深访，N 人，非比例」 | `_qualitative` note（[L940-L950](file:///E:/AI/data/envs/helloagent/myproject/competitor_insight/server/analysis_service.py#L940-L950)） |
| 口碑 | 单点 < 3 条不进榜；分母 < 50 标「样本不足」 | `REPUTATION_MIN_POINTS / MIN_DENOMINATOR`（[L72-L74](file:///E:/AI/data/envs/helloagent/myproject/competitor_insight/server/analysis_service.py#L72-L74)） |

工具返回里直接给 `ratio: null + ratio_hidden_reason`，模型没有机会「帮忙补一个百分比」——这是比提示词约束更可靠的实现方式。

### 5.2 比例什么时候隐藏（汇总）

只要命中任一条件就隐藏比例：车型样本 < 10；本题作答 < 10；战败行 < 5；对比总数 < 10；口碑分母 < 50 时标注而不是隐藏（保留条数）；深访永远不出比例。

### 5.3 多源口径冲突：并列展示，不做加权、不做换算

三类源的性质不同，必须分开表述：

| 源 | 性质 | 能做 | 不能做 |
| --- | --- | --- | --- |
| 定量问卷（1,380） | 抽样调查，按车型 30–41 人 | 结构占比、维度排序 | 代表全市场；推断因果 |
| 深访（63 人，单车 3–4） | 定性原话 | 解释动机、补充语境 | 任何比例、「多数人认为」 |
| 口碑（45,613 条） | 平台评论，自选择样本 | 正负向关注点、原句 | 满意度总体水平；与问卷比例合并 |
| 流通（销量） | 本期**未接入**，不出数 | 无（工具返回空态） | 规模、趋势、市占率任何表述 |

冲突处理规则（写进提示词 + 校验器）：

1. 同一指标出现两个数值（如比亚迪交付量 403,472 / 403000），**并列给出并标注来源与时间**，不做平均。
2. 不同源指向不一致（问卷「价格最重要」vs 口碑「续航抱怨最多」），处理方式是**说明两者测量对象不同**，而不是选一个当结论。
3. 任何跨源「合并结论」（例如「价格既是关注重点又是抱怨点」）只有在两个源各自独立成立时才允许，且必须两个源都给出处。

### 5.4 答案必须带出处与样本量

结论采用「断言 + 出处」结构，由渲染层强制：

| 数字类型 | 必须带 | 示例 |
| --- | --- | --- |
| 问卷比例 | 题号 + 分子/分母 + 样本标记 | `智驾 55%（22/40，Q3_13__14，n=41，小样本）` |
| 均分 | 题号 + 作答人数 | `整体满意度 8.1（Q5_1，作答 39/41）` |
| 口碑 | 平台 + 分母口径 | 负向某标签 `N 条（汽车之家，分母＝该车型两平台去重评论数，五车区间 237–400）`；批次号与批次覆盖数只入接口字段，不上页面 |
| 深访 | `[E#]` + 人数 | `「后排能躺」[E12]（深访 3 人，非比例）` |
| 流通 | 表名 + 口径声明 + 月份 | 流通数据接入后才出数；未接入时不出现任何销量数字，只回空态 |

### 5.5 数字白名单校验（新增，关键防线）

`[E#]` 反幻觉门只校验引用编号，不校验数字。智能化分析必须补一层：

1. 工具结果落一个 `numeric_index`（所有出现过的数字及其口径）。
2. 生成完成后抽取结论中所有数字（含百分比、辆数、人数），逐个在 `numeric_index` 中查找（允许四舍五入到 1 位小数）。
3. 找不到的数字：不给业务看到「未校验」这类免责提示。处理方式是**回退一次重写**；二次仍失败则整条结论不渲染，返回明确错误码与缺失项（沿用 `tile_summary` 的失败即报错、不用模板句兜底的做法），同时把未通过的数字写入后端日志与 `verification` 字段，供验收追溯。
4. 校验器同时禁止「唯一 / 仅有 / 都 / 全部」等全称词出现且条目数 ≥2（沿用现有自由问答提示词第 9 条，[user_insight_agent.py](file:///E:/AI/data/envs/helloagent/myproject/agents/user_insight_agent.py#L163-L166)）。

### 6.2 输入与示例指令

- 占位语改为单车型句式：`输入分析指令，如：这款车用户最在意什么`（原型占位语是跨车型对比，本期不采用）。
- 示例指令全部按单一目标车型设计，共四档（点击只填入、不自动执行，避免误触发）；示例中的车型名一律写「当前车型」或五款在库车型之一，**不使用原型示例车**：
  - 档 1 单车型综合解读（P0）：`零跑B10 的用户最在意什么？和它实际用车体验的落差在哪？`
  - 档 2 自身胜败归因（P0）：`钛3 的战胜与战败原因是什么？战败的用户流向了哪些车？`
  - 档 3 满意度与口碑（P1）：`铂智3X 的满意度短板在哪？口碑负面集中在哪些点？`
  - 档 4 流通走势（P1，依赖未接入数据）：`海狮05 的销量走势怎样？`——流通数据未接入时返回空态说明，不给数字。
- **样例里不出现 A vs B 对比句式**，也不提供「对比两款车」这类入口。
- **样例必须与已上线工具一一对应**，且每条样例在发布前跑通一次，避免「样例点进去就报缺数据」。

### 6.3 流式输出

复用现有 NDJSON 模式（`fetch` + `getReader` + 逐行 `JSON.parse`，[home.js](file:///E:/AI/data/envs/helloagent/myproject/assets/home.js#L1989-L2006)），事件类型建议：

| 事件 | 载荷 | 前端表现 |
| --- | --- | --- |
| `status` | `{stage: "parsing"\|"fetching"\|"writing"}` | 顶部一行状态文本（「正在取战胜战败数据…」） |
| `tool` | `{name, args, ok, rows}` | 追加到「工具调用」折叠区，实时可见 |
| `token` | `{text}` | 结论正文增量渲染 |
| `final` | `{answer, sources[], tool_events[], warnings[], verification}` | 渲染出处表、校验结果、导出按钮可用 |
| `error` | `{code, message}` | 明确说明缺哪个源，不降级成通用文案 |

超时：现网 300 秒；建议本模块 120 秒（`max_iters=8`），超时返回已完成部分并标注「未完成」。

### 6.4 结果区呈现

1. **结论段**：先结论后依据，首句必须交代口径（车型、样本量、时间窗）。
2. **数据出处表**（新增，原型没有）：指标 / 数值 / 分母 / 来源（题号或表名）/ 时间窗，最多 8 行，超出折叠。
3. **工具调用清单**（新增）：工具名、参数摘要、返回条数、成功/失败，默认折叠。
4. **原话引用**（有则显示）：`[E#]` + 匿名编号 + 车型 + 城市，可展开原文。
5. **异常处理**：默认只呈现「通过」与「数据不足（标灰并写缺什么）」两种状态；未通过数字校验的结论不渲染，先回退重写一次，二次仍失败则整条返回错误码，不在页面上给业务写免责说明（见 §5.5）。

### 6.5 追问

- 支持多轮，session 按「页面会话 + 目标车型」维度隔离；切换车型即新会话（避免上一车型的结论被误用到新车型）。

- 不支持把追问结果自动回写到标准化磁贴（两个入口相互独立，这是需求原文的硬要求）。

| 「这款车值不值得买 / 推荐哪款」 | 主观评测，库内无对应证据 | 口碑模块 / 联网检索 |
| 「明年销量多少 / 市场会怎么走」 | 预测类，需模型与历史序列，本模块只做描述 | forecast-engine（Chronos-2 / SARIMAX） |
| 「目标车型的市场份额多少」 | 无上险/终端数据；单车定量样本仅 30–41 人，撑不起份额口径 | 明确拒答，说明缺数据 |
| 「上险量 / 终端交付 / 保险数据」 | 当前无该类数据源，正式流通数据尚未接入 | 明确说「当前无数据源」，不拿销量表顶替 |
| 「A 车和 B 车比一比 / 哪款更好」 | 本期锁定不做跨车型对比 | 引导用上方标准化磁贴逐车查看 |
| 单一固定指标（如「零跑B10 满意度多少分」） | 标准化磁贴已有确定口径，AI 入口只会引入不确定性 | 引导点击对应磁贴卡片 |
| 「帮我改一下这个数据 / 补一条记录」 | 只读模块 | 拒绝，说明只读 |

### 8.2 工程上不做

- 不做跨车型对比：不建对比工具、不留 `models[]`/`compare_with` 参数、不做前端对比入口（含「以后可能要」的占位）。
- 不做通用 SQL 工具、不做原始明细直出（§4.3）。
- 不做多智能体编排（§3.2）。
- 不做流通数据的降级实现：未接入就返回空态，不读现有销量表兜底、不估算。
- 不做与标准化磁贴的联动勾选（需求原文明确要求独立）。
- 不写库、不改 `bci` schema、不改 `app.py` 中深度调研与智能问答链路。
- 不把 AI 结论回写到磁贴、不覆盖已有 AI 结论缓存。
- 不做定时/自动生成报告（属于「报告输出」tab）。
- 不在前端硬编码任何统计数字或「执行步骤」动画。
